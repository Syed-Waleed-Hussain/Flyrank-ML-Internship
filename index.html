Stale by the Numbers: A Decision-Support Model for Content Refresh Prioritization

Refresh / Content Opportunity Scoring
Syed Waleed Hussain
ML Internship Capstone
FlyRank AI
Karachi, Pakistan
Abstract—Content teams routinely manage a portfolio of hundreds or thousands of published pages with no principled way to decide which ones are worth revisiting first. This project asks whether historical engagement, ranking position, and content-age signals can be combined into a directional, decision-support score that prioritizes refresh candidates better than a simple staleness-and-click-through-rate (CTR) heuristic. We define a forward-looking, demand-adjusted engagement-decay label and evaluate a gradient-boosted (XGBoost) model against a transparent rule-based baseline under an identical, leakage-audited evaluation protocol — matched folds, matched rows, matched tie-breaking. Across cross-validated folds, the learned model produced a materially higher Precision@10 and Precision@20 than the baseline, indicating it surfaces a denser set of genuinely declining pages within a fixed review budget. Every output is framed as an observed, directional signal for human review, and the system ships as a reason-coded, action-labeled top-20 queue intended to sit upstream of an existing content workflow.
Index Terms—content decay, search engine optimization, gradient boosting, XGBoost, ranking, decision support, feature engineering

I. Introduction

Every content-heavy site accumulates pages faster than any team can revisit them. Some of that content quietly decays — losing clicks, sliding down the results page, falling out of step with the query it once served — while other pages remain durable performers for years. The business problem addressed here is not whether to refresh content, but which pages, in what order, and why, given a content team's fixed weekly capacity.

Most teams solve this today with a spreadsheet heuristic: sort by age, sort by traffic drop, eyeball the list. That approach is cheap but noisy — it treats a seasonal dip the same as a genuine decline, and it offers no mechanism for explaining why a page was flagged, which makes prioritization decisions difficult to defend or audit.

This capstone builds a Refresh / Content Opportunity Scoring system: a model that ingests historical performance snapshots and outputs a ranked, reason-coded queue of pages most likely to be in genuine decline, alongside a recommended action. The goal throughout is decision support, not automation — the system narrows a large portfolio down to a short, explainable list for a human editor to act on.

II. Data

This project draws on the FlyRank ML Internship Warehouse, hosted on Hugging Face and accessed via DuckDB over hf:// Parquet paths. Consistent with the project's data-handling constraints, the working dataset contains no client names, no real domains, and no raw query text — every page and client is represented by a stable hash identifier (page_hash_id, client_hash_id), and only aggregate, snapshot-level metrics are pulled into the analysis layer.

Each row represents one page at one snapshot in time, with:

  • Engagement metrics — clicks, impressions, and derived click-through rate (CTR)
  • Ranking position — average SERP position at that snapshot
  • Demand context — search volume associated with the page's query cluster
  • Content age — days elapsed since the page's last substantive content update

The analysis spans a rolling multi-month window of snapshots per page, sufficient to compute trailing 90-day deltas (features) and forward 90-day deltas (label — Section III). Pages with insufficient snapshot history to compute a valid trailing/forward window are excluded rather than imputed, to avoid manufacturing signal where none exists.

Safe exclusions. Raw query strings, URLs, and client-identifying metadata are excluded at the SQL extraction layer and never enter the feature or modeling pipeline. Only hashed identifiers and aggregate numeric/categorical fields are used downstream.

B. Label Definition

A page is labeled $\mathit{needs\_refresh}=1$ at snapshot $t$ if, over the forward 90-day window, it experiences a relative CTR decay of at least 15% against its own value at $t$, and its impression trend is not strongly positive over the same trailing window:

$$\Delta_{ ext{fwd}} = ext{CTR}(t+90) - ext{CTR}(t) \qquad (1)$$
$$\mathit{needs\_refresh} = egin{cases} 1 & \Delta_{ ext{fwd}} \leq -0.15 \cdot ext{CTR}(t) \;\wedge\; au_{90}(t) \leq 0 \ 0 & ext{otherwise} \end{cases} \qquad (2)$$

where $ au_{90}(t)$ is the trailing 90-day impression-count slope. This threshold — 90 days, 15% relative decay — was set deliberately as this project's own decision contract: a transparent, defensible definition of "meaningful decline" rather than an attempt to infer or reverse-engineer any external ranking system's internal logic.

C. Baseline

A fully transparent rule is used as the floor the learned model must clear:

$$ ext{flag} = (\mathit{staleness\_days} > 365) \wedge (\mathit{ctr} < 0.03) \qquad (3)$$

This mirrors the static, spreadsheet-driven heuristic content teams already use in practice.

D. Model

An XGBoost classifier [1] is trained on the same feature set via a scikit-learn [2] Pipeline, with class imbalance handled through scale_pos_weight computed strictly from each training fold (never from validation or test rows, to avoid an imbalance-driven information leak). XGBoost was selected as the production model for its strong track record on tabular, moderately imbalanced ranking problems and its status as a defensible industry standard for this class of task.

E. Leakage-Proof Validation Design

Because the label is constructed from a forward window, two leakage vectors were closed simultaneously:

  1. Temporal leakage — a training row is valid only if its full forward label window resolves before a fixed global cutoff date; rows whose forward window would cross into the test period are dropped from training entirely.
  2. Cross-client leakage — within the pre-cutoff training data, cross-validation uses GroupKFold on client_hash_id, so no client's pages appear on both sides of any fold.

The baseline and the ML model are evaluated on identical rows, identical folds, and an identical tie-breaking policy (score descending → staleness descending → page ID ascending), so any performance gap is attributable to the modeling approach itself.

IV. Results

Across cross-validated folds, the XGBoost model achieved higher Precision@10 and Precision@20 than the rule-based baseline (Fig. 1), meaning that within a fixed-size review batch, a larger share of the flagged pages went on to exhibit genuine, demand-adjusted engagement decay. The baseline's fixed threshold cannot weigh partial signals — e.g., a moderately stale page with a sharply worsening position trend — the way the learned model can. V. Limitations

  • Correlation, not causation. A flagged page is correlated with features that predict decline; nothing here identifies why a ranking or engagement drop occurred, or models any search engine's actual ranking algorithm.
  • Algorithm and market volatility. Search ranking behavior, competitive landscapes, and query intent shift over time; periodic retraining is expected to be necessary.
  • Label construction is a design choice, not ground truth. The 90-day / 15% relative-decay threshold is a transparent decision contract, not the only reasonable definition.
  • Partial demand-adjustment. impressions_trend_90d reduces, but does not eliminate, the risk of confusing seasonal or category-wide demand shifts with genuine content-quality decline.
  • No causal validation of recommended actions. Action labels are a rule-based mapping from reason codes; this project does not measure whether taking a given action improves outcomes, which would require a follow-up controlled experiment.

VI. Ranked Recommendations

The system's output is a top-20 ranked action queue rather than a raw score dump. Each row carries the fields in Table III.

Table III — Ranked Queue Output Schema
FieldDescription
page_hash_id,
client_hash_id		Identity, fully hashed
ml_scoreModel's decline-likelihood score (ranking key)
reason_codeUp to two interpretable drivers (STALE_CONTENT, LOW_CTR, POSITION_DECLINE, HIGH_DEMAND_UNDERPERFORM), computed independently of the model
action_labelOne of four deterministic recommendations

The four action labels are: Rewrite Snippet (high query demand, page underperforming its own demand ceiling); Update Content (classic stale + low-engagement decay pattern); Deep Refresh / Rewrite (sharp ranking loss alongside other decline signals); and Monitor / Light Update (flagged, but no single acute driver dominates).

This structure is intentional: an editor should never have to take the model's score on faith. The reason code and action label make each recommendation legible and contestable, consistent with the system's role as decision support rather than automation.

VII. Conclusion

This work demonstrates that a leakage-audited, forward-labeled gradient-boosted model can out-rank a transparent staleness-and-CTR baseline on Precision@K for content refresh prioritization, while remaining fully explainable through independent, rule-based reason codes. The resulting top-20 action queue is designed to sit upstream of an editorial workflow, narrowing a large content portfolio to a short, auditable, and actionable list. Future work includes a controlled holdout experiment to causally validate the recommended actions and periodic retraining to track algorithm and market drift.
